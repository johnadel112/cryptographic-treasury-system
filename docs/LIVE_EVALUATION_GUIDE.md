# Fifteen-minute live evaluation

Before the assessment: install pinned dependencies, pass pytest, reserve ports 5050/6000, open the four-page design PDF and Wireshark captures, and confirm every student can explain every module. Close other demo servers before a runner starts. Rehearse the timings below; a successful automated run does not establish that rehearsal happened.

| Time | Demonstration and observable result |
|---|---|
| 0:00-2:00 | Explain GROUP, ownership and three milestones. Use README fresh `runtime/live1` setup: each owner initializes separately, founder signs, server stays in its terminal. |
| 2:00-4:00 | M1 interactive and M2 noninteractive login; signed ping/spend and ledger. Show server authenticates the identity, not merely a channel probe. Inspect secure capture: public certificate/ECDH then ciphertext. |
| 4:00-6:00 | Open vault and contribute M1/M3: still collecting. M5 completes recovery. Explain authenticated commitments/proofs. Repeat with M2/M4/M5 using a new operation ID, compare files, or show the measured `demo vault` run. |
| 6:00-8:00 | Cast five encrypted ballots for the spend, then three contributions. Show final yes count and >=3 decision; server has no individual plaintext votes. |
| 8:00-10:00 | Stop manual server. `python -m treasury.demo A1`: weak login disclosure, request signature still blocks change, secure handshake blocks MITM. Follow the two proxy TCP legs. |
| 10:00-12:00 | `python -m treasury.demo A5`: same cheating M3 proof, weak recovery fails, secure rejects M3 and substitutes M4. |
| 12:00-13:30 | `python -m treasury.demo A7`: weak total 3, signed total 2 and signature rejection. Explain constant weak transport carrier and fully secure A1 control. |
| 13:30-15:00 | Show `demo vault --n 4 --t 2` and `--n 5 --t 4` saved results, replay capture/log rejection, security limitations, and questions. |

Use the exact manual commands in README, replacing OPERATION_ID with the returned result.id. Demo commands create new independent owner subprocesses and new runtime roots; their result.json and per-program logs remain available after completion. Never present canned output as a current execution. All threshold configurations also run in the subprocess test suite.

## Four-step attack script (each recording <=3 minutes)

1. State the attack goal and precisely which check is disabled.
2. Run the weak case and point to its real failure in the log.
3. Run the same controlled manipulation with the target check enabled.
4. Show the specific verification rejecting it and explain the cryptography.

The runners perform both cases and print a measured summary. A1: read Mallory and member/server logs. A5: read M3 and server logs and compare recovered bytes. A7: show signature failure and corrected final count; explicitly disclose the unsigned-handshake carrier. Optional A3: guessed short challenge succeeds without reading login.secret; secure eight attempts fail. Optional replay: repeated ciphertext and nonce rejection. Do not imply eight A3 trials prove security.

## Evidence and submission checklist

- If capture needs repeating, identify loopback using tshark -D and run the README capture commands. Never overwrite prior evidence; use a new output path.
- Record A1/A5/selected bonus in <=3 minutes EACH using screen-recording software; include explanation, commands and visible outcome. No recordings are generated by the test suite.
- Rehearse this 15-minute sequence with all four students. Resolve unconfirmed name-ID mappings in design sheet, rebuild PDF and verify four pages.
- With explicit authorization, make repository private and invite the exact TA GitHub account; confirm acceptance/access. Preserve contribution history. Do not assume either administrative action has occurred.
- Review integration PR and obtain approval before merging to main. Streamlit remains a separate future phase.
